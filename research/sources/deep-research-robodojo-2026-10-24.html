What controlr should change first

Replace one-action-per-model-turn control with bounded feedback programs, calibrated geometry tools and explicit physical effect checks. Add verified cross-episode repair after that baseline is measured. This recommendation is an engineering synthesis, not a claim that one architecture wins universally. PyRUA supports code cells; URAI and Guava show why feedback cannot simply be removed when batching actions.

PyRUA-Lean · URAI · Guava / Guava-4B · HexaShell

Read the denominators before comparing success rates. Official category-weighted RoboDojo aggregates, equal-task averages, one fixed scene per task, selected subsets, first-attempt success, cumulative success across repaired policies and progress scores measure different things.

Corrections that change the decision

  1. The board exposes both Score and strict success rate (SR). GPT-6-Astra is 28.97 Score / 22.48% SR. SenseNova's 54.17% is an author-run ICL-plus-VLA result, not an official listed no-VLA result.

  2. Official PyRUA-Lean is 55.26 Score / 50.35% SR; its released official RGB configuration does not learn between episodes. Strong code-cell execution and perception tools can matter before any RSI layer.

  3. EmbodiedEvo's current official result is 45.08 Score / 38.95% SR, different from its paper's 44.48 / 37.82. Preserve evaluation version and source.

  4. PhysicalRSI, the official HKU MMLab hybrid entry, is different from the SAIL Physical-RSI reading list. Columbia/Princeton EmbodiedRSI is also different from the earlier PR name used by EmbodiedEvo.

  5. WorldScape-R²SI released full source on October 24. Earlier PR text saying release pending is stale. Its 39.35% official SR includes a WAM.

  6. REAL_RSI's pending 61.92% claim and COAP's 70.24% claim execute compiled task programs with no runtime LLM. They do not establish that a general online agent reaches those rates.

  7. A virtual view of an existing RGB-D point cloud, a physical wrist-camera re-view, learned monocular depth, true sensor depth and simulator object coordinates are different information conditions.

  8. The user's 9/20 general_pickup result is one task's 45% sample result. It is not directly comparable with a category-weighted 42-task aggregate or cumulative solve-at-least-once rate.

Mechanism definitions
Code-cell / program control
The controller writes or executes a multi-action program; note distinguishes online cells from offline compiled policies.
Robot shell / CLI access
Robot operations are accessed through an OS terminal, shell or explicit robot CLI; a coding-agent brand alone does not establish this.
Repair or critic agent
An explicit repair/coding/critic role revises an artifact or diagnoses failed execution; not merely retries within one action loop.
Persistent skills / lessons
Reusable written code, skills, rules or lessons persist beyond one episode; within-episode history alone does not qualify.
RGB triangulation
Explicit multi-view or temporal ray triangulation from calibrated RGB; depth backprojection and ray-plane intersection alone do not qualify.
Wrist-camera re-view
Explicit wrist-view inspection/reinspection; note distinguishes physical camera repositioning from a passive wrist observation.
Visual differencing
Explicit difference/change representation comparing images, rather than generic fresh observation or a visual critic.
Exploration / practice phase
Dedicated physical/simulated practice or development rollouts precede a distinct retained/frozen evaluation artifact.
Multiple candidate reasoning / search
Explicit multiple candidate agents/models/programs or search populations combined/selected; separate planner and critic roles alone do not count.
Distilled coder / tool agent
A smaller coder or reasoning/tool-call model is trained on validated teacher traces; RL-only training and motor-policy distillation are excluded.
Prompt / KV caching
Use of prompt-prefix or KV caching is explicitly reported; ordinary inference context is insufficient evidence.
Geometric preview / overlay
Robot pose, gripper geometry, proposed trajectory or metric orientation is overlaid/rendered for agent inspection; plain scene images do not qualify.
Verified artifact promotion
Candidate code/memory/skill/body changes are checked before persistent acceptance; note states the scope and strength of verification.
Physical outcome feedback
Explicit action-effect, contact, progress or verification feedback changes execution/recovery/termination; beyond an unspecified observe-act loop.
VLA / WAM motor actions
A learned VLA or WAM produces some evaluated robot actions. U may refer to a clearly named hybrid variant; N requires explicit VLA-free scope.
Metric / estimated depth access
Agent or its callable perception tools use depth or reconstructed point clouds at runtime; note identifies simulated/sensor/estimated depth.
Privileged runtime information
Runtime exposes simulator object/segmentation identities, native task verdict/progress, or hidden evaluator/criterion-source metadata. Robot proprioception/calibration, sensor depth and public user task instructions alone do not qualify.

6 · A concrete controlr redesign

These are engineering recommendations inferred from the audited evidence. Estimates assume one engineer familiar with controlr, working simulator integration and existing camera calibration access; they exclude queue time, benchmark rollout cost and hardware procurement. They are not measured project implementation times.

1. Bounded persistent Python runtime

Estimated implementation: 2-4 engineer-days

One model response may inspect cached sensor files, call geometry tools, execute several guarded motions, evaluate measured effects and retry locally. Keep joint/EEF safety checks below the program. Bound native steps, wall time and retries; yield compact evidence at physical checkpoints.

Validation: Paired comparison with the existing per-step loop, holding observations, perception tools, model and physical budget fixed.

2. Calibrated geometry and evidence

Estimated implementation: 3-6 engineer-days

Expose synchronized RGB frames, intrinsics/extrinsics, robot pose, gripper width and source timestamps. Add cross-view triangulation with reprojection residual/uncertainty, known-table ray intersection, projected gripper/target overlays, and physically move the wrist when baseline or visibility is inadequate.

Validation: Separate interface gain from added sensing. Compare passive stereo, an equal-budget physical re-view and the same images without calibrated geometry.

3. Effect checks and adaptive handoff

Estimated implementation: 2-4 engineer-days

Use explicit local guards for reach, grasp-width change, object motion, release and settling. Continue routine free-space segments locally; ask the model when uncertainty, contact mismatch, stall, occlusion or a phase transition warrants it. Use available native modalities only.

Validation: Keep the total sensing/motion budget equal; report model calls saved and paired SR changes. No benchmark success function in runtime decisions.

4. Verified repair and retained capabilities

Estimated implementation: 3-5 engineer-days

A separate episode reviewer proposes one minimal tool/skill change with evidence and a failure hypothesis. Run syntax/unit checks, paired physical development cases and a regression capability bank; then test the merged candidate. Freeze versioned code, prompts, calibration and skill manifests for held-out episodes.

Validation: Report rescued/lost pairs, per-task regressions, acquisition calls and dollars, and held-out SR. Keep raw log retrieval as a comparator to structured skill retrieval.

5. Only then distill or compile

Estimated implementation: 1-2 weeks after sufficient traces

Compile repeatedly successful bounded skills or train a small coder on validated successes, midtask recoveries and rejection decisions. Retain frontier-model fallback for uncertainty. Price data collection and failed acquisition attempts as well as deployment.

Cheap experiments and unresolved evidence

These are gaps in the verified evidence, not assertions that nobody has considered the idea. Related ingredients already appear in the cited projects.

Separate code execution from better tools

A 2x2 experiment: per-step versus bounded code; current versus calibrated geometry/effect tools. Six representative tasks x 20 paired held-out layouts x four conditions = 480 episodes, after distinct development scenes.

PyRUA supports code representation, while URAI and Guava show that useful runtime decisions and feedback cadence can outweigh batching. This design identifies the interaction in controlr's own setting.

Uncertainty-triggered physical re-view

Under the same action/image budget, compare fixed passive stereo, always taking a wrist re-view and re-view only above a triangulation uncertainty/occlusion threshold.

CodeActionBench and PhysEvo use physical re-views, but no matched RoboDojo ablation isolating the uncertainty trigger was verified.

Calibration-dependent skill invalidation

Attach camera/tool-tip/gripper calibration versions to every retained skill. Perturb one estimate in development; compare blindly retained skills, whole-library invalidation and dependency-specific revalidation.

KnowBody motivates dependency tracking; its effect on a RoboDojo coding-agent skill library remains unverified.

Execution acknowledgments and stale-image rejection

Require every action to return an executed-step prefix and observation epoch. Inject realistic interrupted chunks or stale frames in development; compare continuation from planned actions against measured executed actions.

WorldScape and OpenETA contain related lifecycle controls; no matched independent RoboDojo success ablation was located.

Repair for another task, not just the failed task

Accept a candidate only after paired failure cases and a task-diverse capability bank; report seed holdout and task holdout separately. Compare generic tool repairs with task-specific recipes under equal acquisition budgets.

Most strong submissions retain task-specific engineering. RPG and SimEX support regression replay, but generic transfer versus task specialization is still incompletely separated.

Value per model call and per acquired skill

Compare fixed-step, phase-triggered and anomaly-triggered calls with all-attempt dollars/tokens/time per success. Include repair, abandoned generations, failed runs and API retries.

Existing costs often condition on successes or omit acquisition. robot-agent-eval already proposes related factorial designs, so this is a useful evidence gap, not an untouched idea.

Measurement contract: report paired rescued/lost episodes, strict SR and progress separately; stratify by task; retain failed and interrupted attempts in resource accounting; report native steps, model calls, input/output/cached tokens, wall time, acquisition cost and deployment cost. Freeze code, prompts, skills, perception versions, calibration and sensor permissions before the held-out run. A unit test is not evidence that a physical skill works.
