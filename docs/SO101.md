# SO-101 rig: real arm with a camera on the gripper

controlr drives a LeRobot SO-101 follower (5 joints + gripper, Feetech STS3215) whose only
camera rides on the gripper. The model sees the wrist image, a STATE line and a VIEW line, and
replies `MOVE ee_delta dx dy dz` / `GRIP` / `STATUS` as everywhere else.

```
 rig (sp@192.168.1.22, LAN)              Mac (jump host)         controlr (local)
 so101 server (LeRobot's python)   <-  ssh -L 7811  <-  ssh -L 7811  <-  So101Robot  -> LLM router
   Feetech bus, wrist camera, stop rules                                 envelope, IK, loop
```

The rig cannot reach the LLM router, so controlr runs elsewhere and reaches the server
(localhost-only, HMAC key) through ssh tunnels.

## Geometry the model gets

* Base frame = URDF `base_link`: origin on the table under the base, x forward, y left, z up;
  table z = 0. TCP = `gripper_frame_link`, between the jaw tips.
* LeRobot's `DEGREES` joint reading (zero = middle of the calibrated range) is the URDF's
  "new calibration" zero, so encoder angles go into FK unchanged — up to the per-joint
  `robot.params.joint_offsets_deg` (model angle = measured + offset; see "Joint zero calibration").
* 5 joints: the tool keeps a fixed pitch (`tool_pitch_deg`, default 60 below horizontal) and
  roll (`tool_roll_deg`, default 90: the stock wrist camera upright, image up = forward, jaws
  closing sideways) and always points away from the base (`kinematics.reachable_rotation`).
  `rotation: yaw` works only with `tool_pitch_deg: 90` (straight down: reach z <= ~100 mm).
  Reachable at pitch 60: x ~140..380 mm, z up to ~150 mm.
* VIEW line every turn: which way +x / +y run in the current image from the jaw tips (the
  camera moves, so the manual cannot state fixed directions).

## Safety (in code, below the model)

1. `CartesianEnvelope`: workspace box, table clearance, 50 mm per MOVE line (`configs/so101.yaml`).
2. Client: IK every 5 mm; an unreachable stretch shortens the move (WARN); the target
   orientation is always the reachable one.
3. Server: goals clamped to the calibrated range minus 3 deg; peak joint speed <= 1 rad/s;
   TCP speed `safety.max_tcp_speed_m_s` (0.05 m/s); a joint more than 12 deg behind its goal
   for 3 ticks (or above `current_stop_ma`, off until tuned) = blocked → the arm freezes where
   it is (STOP); power-up sets Goal = Present before torque on.
4. Ctrl-C on the server: freeze; twice within 3 s: torque off (THE ARM FALLS) and exit.
   `shutdown` op / normal exit: slow move to the rest pose, then torque off.
5. **A human at the arm's power switch for every motion.** The arm is light and slow, but its
   reach covers whatever stands in front of it — clear the workspace (the rig laptop sat in it
   on 2026-10-14).

## Serial ports

Both arms' CH340 adapters share one `/dev/serial/by-id` name, and `/dev/ttyUSB0/1` (and the USB
socket paths) swap on re-plug. A wrong guess is worse than a refusal: LeRobot's `connect()` then
offers to write one arm's calibration into the other arm's motors (Homing_Offset and the position
limits, EEPROM), after which the motors' Homing_Offset no longer says which arm they belong to.
So ports default to `auto` (server `--port`, `SO101_PORT`; recorder `--follower-port` /
`--leader-port`): `arm_id.py` reads raw Present_Position and Homing_Offset on every `/dev/ttyUSB*`
(no handshake, nothing written) and scores each port against each calibration file:
`pred = (raw + motor_offset - file_offset) mod 4096` must fall inside the file's
`[range_min, range_max]` (40 ticks of slack for a joint resting on its stop). The right arm at a
normal pose gives 0 joints out, the other arm's file several (2-3 on the rig). The one assignment
with 0 out wins; none (an arm missing, unknown, or far outside its range: move it to rest) or more
than one (pass the ports) = refused, with the score table printed. Explicit ports are checked the
same way. The guard stays: an arm whose motors do not hold its own file is refused (nothing is
written); the recorder says whose calibration they hold, and `--restore-calibration` writes the
arm's file back into its motors (only when arm_id identified the arm and its torque is off; it
then sets Goal = Present and prints old -> new per joint).

Tunnels (the rig's ssh needs a password from the Mac; the Mac is `ssh mac`):

```bash
ssh mac 'ssh -fN -L 127.0.0.1:7811:127.0.0.1:7811 sp@192.168.1.22'   # Mac -> rig
ssh -fN -L 127.0.0.1:7811:127.0.0.1:7811 mac                          # here -> Mac
```

## Calibration

`uv run --with opencv-contrib-python python scripts/so101_calibrate.py board board.png` → print
at 100 %, measure a square; `... intrinsics --square-mm <s>` (no motion: wave the board);
`... handeye --square-mm <s> --board-x 0.26` (board flat on the table; the arm visits 15 poses).
Output `~/.config/controlr/so101_wrist.json` → `robot.params.camera_calib`. Its check numbers:
the board origin's z in the base frame should be ~0 mm (table), the spread over views a few mm.
Until then the camera pose is the stock mount from `so101_new_calib_camera.urdf` (the VIEW line
directions are right, the pixel lengths approximate) — keep `renderers: [raw]`.

## Joint zero calibration

The mid-range zero is only as good as the calibrated range: LeRobot's ranges are 2-14 deg wider
than the URDF's limits, so FK can be several degrees off per joint (the TCP read ~22 mm below the
table while the jaws held a ball lying on it). `robot.params.joint_offsets_deg` (5 values, deg,
`[pan, lift, elbow, wrist, roll]`, default zeros) corrects it in the client only: model (URDF)
angle = the server's measured angle + offset, and everything sent to the server (home, paths,
goals) is model - offset; the server's limits are shifted the same way. The server, its logs and
teleop recordings stay in LeRobot's DEGREES.

Recording (on the rig, `scripts/so101_teleop_record.py --out .../touch_1`, leader + follower):
close the jaws fully, then touch the closed jaw tips to the table and hold still ~1 s, 10-15
times: near and far (150-350 mm in front of the base), left, centre and right, and with the tool
steep (pointing down) as well as tilted 30-45 deg. The variety is what separates the joints: a
steep tool makes the touch height almost blind to wrist_flex, a single reach cannot tell
shoulder_lift from elbow_flex. Touch lightly (the arm is compliant), and end in the rest pose.

Fit (here):

```bash
uv run python scripts/so101_fit_offsets.py demos/touch_1 [demos/touch_2 ...] --out runs/so101_joint_offsets.json
```

It finds the touches (all joints within 0.5 deg for >= 0.6 s, gripper <= 8 %, shoulder_lift above
-90 deg = not the rest pose), prints them with their FK TCP, fits the shoulder_lift, elbow_flex and
wrist_flex offsets so that every touch's TCP is at z = 0 (regularised least squares, prior 0 +- 10
deg, 2 mm per touch), and prints the residual per touch, the offsets with rough std, warnings when
the touches do not pin a joint down, and the TCP of the ball-grasp and rest poses with the offsets.
Put its `joint_offsets_deg` into `robot.params`. shoulder_pan cannot change a height (vertical
axis) and wrist_roll barely does: both stay 0. `--fit-dz` also fits a base height (table not at
base z = 0); it trades off against the joint offsets unless some touches are on a block of known
height (`DIR@60` = the touches in DIR are on a surface 60 mm up). A residual rms well above ~2 mm
means the URDF itself differs from the arm, or the touches pushed into the table.

## Known gaps

* No automatic success check: `trust_done` + operator verdict.
* `current_stop_ma` is off: log the peaks (`turns.jsonl` → `backend.runs[].peak_current_ma`)
  on free moves first, then set it above them.
* The gripper's width map is linear 0..100 % → 0..70 mm (not measured).
* Gravity sag: LeRobot's P=16 leaves loaded joints short (first jog: 5-13 mm low per move). The
  server offsets the goal by the measured error after each move (capped 8 deg, carried into the
  next move, cleared by a stop): jog error after it ~1 mm. The arrival WARN (> 10 mm) remains.
* Only ONE jaw shows in the wrist image at the default home (the stock mount guess is off):
  "centred between the jaws" is not observable until the hand-eye calibration says where the
  camera really is (and perhaps a different `tool_roll_deg`).
* Restarting the server while the arm holds itself up would drop it (configuring the motors
  needs torque off): the server refuses to start with torque on; park first (`shutdown` op).
