# 2026-10-25: does the hybrid agent's model matter end to end? (RoboDojo proxy eval, mode B)

**Question:** with the same manual, API and procedure, do GPT-6 Astra-high, GPT-6.1 Sol and Claude Sonnet 5.5
differ in success when they drive the hybrid agent, which picks a skill or writes code cells over `robo`, end to end?

**Hypothesis:** the code-heavy tasks separate the models; on the skill tasks, the models are equal because the
skill decides the outcome.

**Setup:**
- **Policy:** `dojo.agent.policy:AgentPolicy` on integration's `RuntimePolicy(program=...)`.
- **Mode B:** perception estimate, looks and search. Verify is off, identical for every arm (lead's decision).
- **Agent:**
  - manual v3 (v2's instruction-pattern conventions + `robo.place(over=)` and `robo.pick(lift=)`) and appendix
    agent_v4;
  - a `python(code)` function tool is declared for every model (see the bug below);
  - at most 30 LLM calls per episode; a cell is bounded at 250 env steps or 4 contacts;
  - head frame at turn 0 (640 px), then up to 3 frames of 448 px per turn (after contacts, and `robo.show`);
  - append-only transcript, prefix-cached.
- **Tasks:** cover_blocks, general_pickup, put_bottles_into_dustbin, align_blocks, build_tower and stack_bowls,
  on settled dev layouts 100000 and 100001.
  - stack_bowls replaces press_by_number, which cannot run in mode B: perception's catalogue has no SpringButton or
    number_card.
  - press_by_number runs separately in mode A (GT state).
- **Batching:** one bundle job per task runs all three models (`AgentConfig.models` cycles by the episode
  counter), layout by layout. Proxy eval: Isaac 5.1 physics-only RoboDojo episodes with Isaac 6.0 frames, not the
  official renderer.
- **Code:**
  - feat/dojo-agent at the commit in each row's `agent.code_commit`;
  - perception is feat/dojo-perception de21b05 from AGB_general_pickup on;
  - the earlier general_pickup Sonnet row ran on the older perception and agent_v3 (no tool).
- **Runs:** `compute3:~/dojo-data/integ/runs/AGB_<task>/` (episodes.jsonl, per-episode agent logs under `agent/`).
  Summaries: `python -m dojo.agent.e2e_report <dirs> --md | --episodes`.

## A bug the first batched job found (fixed before every number below)

On the cx/ route, GPT-6 Astra and Sol answer a code cell as a call of a `python` tool, the way they are hosted in
Codex. We had not declared a tool, so omniroute dropped the call: the stream carried only `reasoning_content`,
with `finish_reason: stop` and about 100 completion tokens. Astra lost 14 of 16 replies to this and Sol 10 of 14;
on one empty reply, Sol answered `finish()` at step 21.

Phase 1 was not affected: it asked for JSON, not code. Fix: every request declares `python(code)`; the client
assembles streamed `tool_calls`; the loop stores a call as a fenced cell. AGB_general_pickup's OpenAI episodes
are therefore invalid and were rerun as AGB_general_pickup2.

## Failure modes

- **The perception and skill layers decide most outcomes, not the model.**
  - stack_bowls 0/6 and build_tower 100000 0/3 are perception_gross for all three models, with the same bowl /
    block error in each.
  - put_bottles 0/6 are `put_into` drop misses or pick collisions. All models re-tried with the skill and then
    with code (`move_to` + `grip`) and ran out of steps.
- **Following a convention literally** ("lift at least N cm; keep holding it"):
  - Astra and Sol wrote `pick(lift=0.10); finish()`, which opens the grippers at once.
  - Sonnet lifted 0.12 and held.
  - This is the same direction as Phase 1, where Sonnet followed checker conventions best.
- **Creativity when a tool is missing:** on align_blocks, Astra-high used the fingertip as the pusher once the set
  square proved ungraspable, and succeeded on one layout. Sonnet tried 4 grasp methods, then servoed the set
  square with `grip` + `move_to`; Sol gave up after 2 failed picks.

## Conclusions (given n)

- n = 12 episodes per model, over 6 tasks and 2 layouts. **5/12, 5/12 and 4/12 are indistinguishable.** 20 episodes
  per arm would resolve only a ~40-point difference.
- End to end, the model is not what limits the hybrid agent today: perception and skill failures do. Every model
  made the same skill-or-code decision in every episode.
- The differences that do show are behavioural and match Phase 1:
  - Sonnet follows checker conventions more literally (general_pickup 2/2 against 1/2);
  - Astra-high improvises a little better when the API lacks a tool (align_blocks 1/2).
- **Recommendation:** keep **Sonnet 5.5 at default effort** as the agent model.
  - It has the best grounding (Phase 1: 162/162 with manual v2) and the same end-to-end success.
  - Per call it is the fastest in Phase 1 and equal here (LLM time ~65 s per episode for all three).
  - It costs more output tokens.
  - Astra-high buys nothing measurable at this n. Re-test it after perception and skills improve: when
    perception_gross is gone, the remaining failures will be the model's.
- press_by_number with the v2 convention is 6/6 in mode A. The convention line is the cheapest win on the board
  (Memory weight 1/30). It needs perception's SpringButton / number_card assets to run in mode B.

## Found along the way, for the BACKLOG

- cx/ GPT-6 needs a declared tool for code replies (DEVELOPMENT pitfalls).
- The scene must list functional frames (pegs, slots) for `stack_on_pegs` / `slots_and_press`.
- The set square has no grasp in the skills layer.
- Mode B: put_into drop misses and bowl perception.
- `skills_called` is updated only after an LLM call, so an episode that ends inside its first cell reports no
  skills. The first-cell column in the per-episode table comes from the transcript.
