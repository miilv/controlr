## 3. The route problem (written up; not fixed here)

`copy_demonstration` is reached through `dojo/runtime/supervisor.py`'s `Vocabulary("imitate_sorting_sequence", …)`.
An instruction regex picks a task name, and the task name picks the skill. That is the task-keyed route the hard rule
forbids. The fix belongs in the shared planner path (the partner's model planner over the shared library).

**What a general entry point needs:** a planner-callable verb in the shared library, with arguments in scene words.
For example: `imitate(demonstrator, demo_container, our_container, objects=None)`.

- `demonstrator`: a scene actor that is not ours (the support robot the scene description names);
- `demo_container`: where the demonstrator puts things;
- `our_container`: where ours go;
- `objects`: optional, defaults to every movable object not inside a container.

The planner chooses the verb from the instruction ("observe … then place the corresponding objects … in the same
order"). No task name, no vocabulary.

**What IMIT2 already has that fits:**
- `wait_demo_done` / `wait_support_home`: generic "actor at rest / back home" reads.
- The departure read (`watch_read` sources) and `imitate_order` persist / elim: "which objects left their places, in
  what order", for any actor.
- `dojo.perception.twin_match`: a generic appearance correspondence between two object sets.
- `put_in_open` with `reach` and `refind`: generic put-into-container with reach-aware handover and re-find.

**What is still task-shaped and must change for the general verb:**
- `demo_side` = "the farther half of the movers": it assumes the demonstrator's objects are half the table. Replace
  with "the objects the demonstrator's arm reaches", or the objects whose departures were read.
- The `max_wait` / `after_last` / `gone_quiet` defaults were tuned to this task's demo.
- The `imitate_*` config names.
- The container labels the planner passes today.

The BACKLOG item records the same list.

## 4. Demo timing — measured, not fixed

**Public mechanics (RoboDojo code only; no `Traj` / `Eval_Layout` file opened):**
- `env_cfg/sim/sim_config.yml` `dt: 0.004` and `env_cfg/arx_x5.yml` `collect_freq: 25`. In
  `obs_manager.collect_interval` this gives 1 / (0.004 × 25) = **10 sub-steps per env step**.
  `eval_env.process_control_info` pops that many support-arm sub-steps from the demo per policy action. A demo of N
  sub-steps therefore lasts N / 10 env steps.
- The demo format (`load_support_arm_traj`, `robot_manager.plan_ee(need_plan=False)`) is per-segment
  position / velocity arrays at the sub-step rate. That is exactly what RoboDojo's own planner returns
  (`env/planner_manager/curobo_planner.py` `plan_path` → `get_interpolated_plan()`, `interpolation_dt = dt`).
- The Franka's limits: URDF joint velocities 2.175 rad/s (j1–4) and 2.61 rad/s (j5–7); `Assets/Robots/franka/
  curobo.yml` `max_acceleration 15`, `max_jerk 500`, no velocity scale. A gripper move is 100 sub-steps
  (`plan_endeffector_joint` default, 90 % interpolation).
- The script that generated the official demos is **not public**. What is public is the planner and timing it would
  use.

**Why ours run longer.** `dojo/simlab/demo_gen.py` plans with cuRobo, then re-times every segment to slow per-sub-step
caps:
- `DQ_FREE` 0.008, `DQ_CARRY` 0.005 and `DQ_NEAR` 0.003 rad per sub-step (2.0 / 1.25 / 0.75 rad/s), divided by
  `--speed`;
- at least 40 sub-steps per segment;
- `SETTLE` 30 sub-steps before each close, and gripper actions of 100 + a 50-sub-step hold;
- a 900 env-step acceptance cap.

**Numbers** (`scripts`: `~/imit2-data/scripts/demo_timing.py`, recorded in the journal). Our timing is each pickle's
own length. Public timing takes the same geometric path segments at the Franka's public velocity / acceleration
limits (trapezoidal minimum time, jerk ignored), with each gripper action at 100 sub-steps.

| Demos | ours: min / median / max env steps | motion / gripper (median) | public timing: min / median / max | motion / gripper (median) |
|---|---|---|---|---|
| IMIT2 fresh salt, 19 (speed 1.25; 100021 at 1.5) | 570 / **795** / 900 | 670 / 125 | 412 / **473** / 520 | 373 / 100 |
| canonical dev 100005–09, 100024–29, 11 | 630 / **752** / 896 | 627 / 125 | 440 / **493** / 546 | 393 / 100 |

REPRO's 669–728 on 100000–04 sits inside our range. Under the public timing, our own waypoints would take
**~410–550 env steps**, below the 640 that the official demos are thought to stay under. The slow re-timing accounts
for ~250–300 of the ~300 extra steps, the longer grip-and-hold for ~25.

**How to match (proposed; not implemented):** a `demo_gen --timing public` mode.
- Keep cuRobo's own time-parametrised interpolation at `dt` = 0.004 s under the Franka's public limits (no
  `retime` caps, no 40-sub-step floor).
- Gripper actions of 100 sub-steps with RoboDojo's 90 % interpolation; no extra settle / hold.
- Validate exactly as today (RoboDojo's post-demo check, no t-object moved), and report every rejected demo.
  Fast descents once left the hand lagging above the object at the close; that is what the validation must catch.
- Expected ~410–550 env steps. It should also shorten the reset / demo stall behind the 100001 watchdog kills.

**Caveat:** the estimate times OUR waypoint sequence (31 moves and 10 gripper actions per demo); the official
waypoints are unknown. The trapezoid bound ignores jerk and the Franka's PD tracking lag, so real lengths will be
somewhat longer.

**Provenance flag for the lead:** two comments in `demo_gen.py`, from commit `41a8c94a`, quote numbers measured on
RoboDojo's own make_kong / tic-tac-toe demos ("median 0.002, peak 0.008 rad/sub-step"). Its constants were
originally set from those official `Traj` files (25 Oct, before the current rule). Nothing in this round uses them.
The `--timing public` mode should replace them.
